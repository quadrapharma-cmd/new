# 03 — UX specification: screens, every user scenario, design system

## 1. Personas

| Persona | Goal | Pain today | What they need first |
|---|---|---|---|
| **Mona, RA specialist** at a local manufacturer (preparer) | File a new generic under One Submission | Screening rejections; repeated M3 comments | «What exactly do I need?», checks before submission |
| **Dr. Karim, RA manager** (reviewer/approver) | Approve several dossiers a month | No visibility of readiness; risk | A readiness dashboard and an approval gate |
| **Sara, scientific office** of an importer | Imported generic with a CPP | Legalisation lead times; translation declaration | Third-party tracker with reminders |
| **Consultant** with many clients | Prepare dossiers for several companies | Switching rules and letterheads | Workspaces per client |
| **Junior pharmacist** | Learn while doing | Doesn't know the rules | Explanations with sources, guided wizard |

## 2. Information architecture

```
Workspace switcher ▸
├─ Home (dashboard: all dossiers, readiness, due items, alerts on rule-pack updates)
├─ Dossiers
│   └─ Dossier ▸ Overview · Profile · Requirements · Documents · Data (Product/APIs/Formula/Batches/Specs/Stability)
│                · Generate · Variations · Sequences · Export · Activity
├─ Library (parties, signatories, letterheads, reusable documents e.g. GMP certificates)
├─ Rule packs (versions, changes, sources)
└─ Settings (users & roles, language, storage, licence)
```

## 3. Screens (layout and behaviour)

1. **Home dashboard**
   - Cards: dossiers in progress, ready to export, blocked, waiting on third party.
   - Table of dossiers: product, type, activity, pack set, readiness %, blocking count, owner, last change.
   - Alerts strip: «New EDA document: NP.CAPP.065 v6 adopted — 7 dossiers affected → review».
2. **New dossier wizard** (6 steps, progress bar, save and resume at any step):
   1. Product.
   2. Type and activity (dossier kind, origin, licence, new / re-reg / variation, decree case).
   3. APIs and manufacturers (option per manufacturer).
   4. Dosage specifics.
   5. Parties (pick from the library or add).
   6. Rule-pack set (in-force / preview drafts) and confirm.
   - The live right panel shows «You will need 58 documents — 21 we can generate for you».
3. **Dossier overview**
   - A readiness ring per module (M1/M2/M3/M4/M5).
   - A «next best action» list.
   - The approval state and the last export.
4. **Requirements board** (the heart of the product)
   - Grouped by module and section; filters by status, origin, class and «assigned to me».
   - Each row:
     - status chip;
     - title (AR/EN);
     - source link (e.g. «NP.CAPP.065 §1.1.13»);
     - documents count;
     - action button, which changes with the state: Upload · Generate · Fix · Rebuild · Request from issuer · Waive.
   - A side drawer opens the slot with:
     - acceptance criteria as a checklist;
     - check results;
     - version history;
     - comments.
5. **Document viewer**: the PDF on the left; the checks on the right, each with a severity, a reason, the source and a one-click fix with a before/after preview. Locked documents show a 🔒 banner explaining why.
6. **Data editors**: spreadsheet-like grids for the formula, batches, specifications and stability. Calculations are visible; paste from Excel is supported.
7. **Generate**:
   - a template gallery (Annex I, composition, salt calculation, commitments, justification, cover letter…);
   - for each template: the missing fields listed in red, an EN/AR preview, then «Create DOCX & PDF».
8. **Variations**:
   - search the catalogue → card with PAC, conditions checklist, requirements, CTD sections;
   - add to the basket → grouped class shown → «Create variation sequence».
9. **Sequences (eCTD)**:
   - a timeline of sequences;
   - a lifecycle view per leaf (current / cumulative);
   - the tracking table.
10. **Export**:
    - choose CTD / eCTD 3.2.2 / eCTD 4.0;
    - the pre-export gate checklist;
    - the provisional-profile acknowledgement;
    - export progress, then the package plus the validation report;
    - «How to submit» card (the right EDA form link for the decree case).
11. **Activity / audit**: who did what, when, with the hashes.
12. **Rule packs**: list, diff between versions, sources (PDF links), and an «affected dossiers» list.

## 4. Design system («modern business»)

- **Layout:**
  - left (LTR) or right (RTL) navigation rail;
  - top bar with workspace, search (Ctrl+K command palette) and language toggle;
  - content max-width 1440, a 12-column grid, density «comfortable/compact».
- **Typography:** Inter for Latin, IBM Plex Sans Arabic for Arabic. Scale 12/14/16/20/24/32; tabular numbers in tables.
- **Colour tokens** (light; dark mode mirrors):

| Token | Value | Use |
|---|---|---|
| `--bg` | #F7F8FA | App background |
| `--surface` | #FFFFFF | Cards |
| `--ink` | #0F172A | Text |
| `--muted` | #64748B | Secondary text |
| `--brand` | #0E7C86 (teal) | Primary actions |
| `--brand-2` | #1E3A8A (indigo) | Accents and links |
| `--ok` | #16A34A | Conforming |
| `--warn` | #D97706 | Needs attention |
| `--bad` | #DC2626 | Non-conforming |
| `--wait` | #7C3AED | Waiting on third party |
| `--na` | #94A3B8 | Not applicable / not started |

- **Components:**
  - status chip (icon + text, never colour alone);
  - readiness ring;
  - stepper;
  - drawer;
  - data grid;
  - toast;
  - empty states with a primary action;
  - skeleton loaders;
  - confirmation dialogs for destructive or locked operations.
- **Motion:** 150–200 ms ease-out; nothing blocks input.
- **Accessibility:**
  - WCAG AA contrast;
  - full keyboard use;
  - focus rings;
  - ARIA live regions for check results;
  - RTL mirroring of layout and icons where directional;
  - CTD codes and numbers stay LTR inside Arabic text.

## 5. Scenario catalogue (every situation the user can hit)

Format: **trigger** → system behaviour → user action. «S» = success path, «A» = alternative, «X» = error/exception.

| X2 | Storage folder full or not writable → blocking dialog with the space needed and «choose another folder» |

## 6. End-to-end journeys used as automated tests

1. Local generic FCT, new, CEP + DMF APIs → CTD export.
2. Imported generic capsule, re-registration, legalised CPP pending → 🟣 → arrives → export.
3. Under-licence local, non-English leaflet → translation declaration.
4. Powder for injection with solvent.
5. Re-registration, old molecule → justifications.
6. CEP withdrawn mid-way → switch to DMF.
7. Variation: new API manufacturer (PAC-II).
8. Grouped variation PAC-B + PAC-II.
9. First eCTD with baseline.
10. Response sequence.
11. Rule-pack update v5 → v6.
12. Locked third-party document edit attempt (negative).

Each journey runs in Arabic and English, at 1440 px and 1280 px.

## 7. Content and tone

- Messages answer three things: **what** happened, **why** (with the source) and **what to do**. Example: «CPP does not name Egypt as importing country — required by NP.CAPP.065 §1.1.13 → request a corrected CPP from the issuing authority [Generate request letter]».
- Arabic UI copy is clear Modern Standard Arabic. Generated letters to EDA use formal Arabic; CTD terms stay English.
